# Choose the learning's owner

Use the repository's actual authorities and formats. A test may fully capture the
learning; add prose only when future work also needs procedure, scope, or rationale.

| Need | Destination |
| --- | --- |
| Prevent a reproducible defect | Regression test or executable check at the owning seam. |
| Improve an existing repeatable workflow | Its skill or runbook; update the canonical rule. |
| Preserve a durable architecture choice | The repository's ADR process, including acceptance and supersession rules. |
| Define producer/consumer behavior | The canonical service contract and relevant compatibility evidence. |
| Record current topology, capacity, or deployment | Dated system documentation with evidence and a refresh method. |
| Govern future work throughout a tree | The nearest applicable repository instruction file. |
| Explain one change | Its authorized PR or commit context. |
| Track unimplemented work | An issue, only when an external write is authorized. |
| Preserve no useful future action | No durable change. |

Create a new skill only for a recurring non-obvious workflow with no existing
owner. Avoid generic learning archives unless the repository deliberately uses
one. Search for equivalent or stale content and update it in place; preserve
historical records through their established supersession process.
